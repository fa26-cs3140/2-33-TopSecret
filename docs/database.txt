Database and Persistence

HTTP SESSION STORAGE

The web server adds no tables, columns or persistent session store.
controller.InMemoryWebSessionStore maps random 256-bit tokens to usernames in a
ConcurrentHashMap. Tokens, passwords and web sessions are never written to the
database, logs or documentation. Logout removes the token; shutdown clears the
store. Restarting the process invalidates all sessions. Each protected request
resolves the current account role through model.AuthenticationService.

model.SqliteContentService handles web reads through the same list/read/audit
methods as the terminal. Successful record/list reads retain existing READ audit
transactions. Web POST requests cannot create/update/delete content. Login/logout
do not create content audit entries. Schema declarations below remain unchanged.

All relational content, the audit log and agent messages live in data/missions.db.
Credentials remain in the separately ciphered data/credentials.cip file.


DATA SOURCES

  mission_briefs.tsv    legacy mission title, date and brief text; also seeds the briefs table
  facilities.tsv        facility name and abbreviation
  agents.tsv            agent name and birth date

SqliteMissionRepository owns the mission import. SqliteContentService owns the
content tables, facility/agent imports, mission relationships and
content mutations. SqliteAuditLogRepository owns audit-log reads and standalone
writes. SqliteMessageService owns the messages table. Connections are opened per
operation and always closed afterward.


CONTENT TABLES

  missions
    id INTEGER PRIMARY KEY AUTOINCREMENT
    title TEXT NOT NULL
    brief TEXT NOT NULL
    date TEXT NOT NULL

  briefs
    id INTEGER PRIMARY KEY
    title TEXT NOT NULL
    date TEXT NOT NULL
    text TEXT NOT NULL
    mission_id INTEGER NULL
        REFERENCES missions(id) ON DELETE SET NULL

  facilities
    id INTEGER PRIMARY KEY
    name TEXT NOT NULL
    abbreviation TEXT NOT NULL

  agents
    id INTEGER PRIMARY KEY
    name TEXT NOT NULL
    date_of_birth TEXT NOT NULL
    date_of_death TEXT NOT NULL
    notes TEXT NOT NULL
    facility_id INTEGER NOT NULL REFERENCES facilities(id) ON DELETE RESTRICT

Briefs are separate records that may be attached to a mission through the optional
mission_id foreign key. They are seeded from the same file on first start. Blank strings represent
an unknown date of death or empty notes. Every nonblank date is ISO YYYY-MM-DD.

briefs.mission_id relates a brief to the mission it documents. It is nullable
because a mission may have zero briefs and a brief need not belong to any
mission, and because briefs existed before missions did. ON DELETE SET NULL
rather than CASCADE: a brief is a record in its own right and outlives the
mission it documented. A brief belongs to at most one mission, which is why this
is a column rather than a join table; attaching a brief that already has a
mission moves it.

Because missions is referenced here, missions is created before briefs. A
database created before this column existed is migrated on the next
initialize, which adds the column when it is missing rather than only working
on fresh databases.


MISSION RELATIONSHIPS

  mission_facilities
    mission_id INTEGER PRIMARY KEY
        REFERENCES missions(id) ON DELETE CASCADE
    facility_id INTEGER NOT NULL
        REFERENCES facilities(id) ON DELETE RESTRICT

  mission_agents
    mission_id INTEGER NOT NULL
        REFERENCES missions(id) ON DELETE CASCADE
    agent_id INTEGER NOT NULL
        REFERENCES agents(id) ON DELETE RESTRICT
    PRIMARY KEY (mission_id, agent_id)

The primary key on mission_facilities permits at most one facility per mission.
Initialization creates the one required row for every imported mission. A trigger
rejects deleting that row while its mission exists.

The composite key on mission_agents prevents duplicate assignments. Initialization
creates at least one assignment for every imported mission, and
ContentService.assignAgent adds further ones; it inserts OR IGNORE, so assigning
an agent already on the mission changes nothing.

Nothing relates an agent's own facility to the facility running the mission, so a
mission may draw agents from any facility and an agent may serve on several
missions. That is required behaviour, not an oversight, and
SqliteContentServiceAgentTest pins it so a later constraint cannot remove it.

ContentService.setFacility updates an existing mission_facilities row in place
instead of deleting and reinserting it, because the delete trigger below refuses
to leave a mission without a facility. A trigger rejects
deleting the final assignment while its mission exists. Deleting an entire mission
is valid and cascades its relationship rows. Deleting a referenced agent or
facility is rejected.

SQLite disables foreign-key enforcement by default per connection. Every
SqliteContentService and SqliteMessageService connection executes
PRAGMA foreign_keys = ON before use.


SAMPLE IMPORT AND RESTARTS

SqliteMissionRepository imports mission_briefs.tsv only when missions is empty.
SqliteContentService imports facilities.tsv and agents.tsv only when their target
tables are empty. Repeating initialize therefore creates no duplicate records or
relationships.

The supplied facility and agent files contain no header and no relationship ids.
Rows import in file order. Agents receive facilities round-robin. Missions receive
facilities and one initial agent round-robin. The mapping is deterministic, so a
fresh database always receives the same relationships.

Agent birth dates arrive as names such as "June 14, 1985" and are stored as
1985-06-14. Facility insertion, agent insertion and relationship insertion share
one transaction. Any malformed row or SQL failure rolls the transaction back.
Missing seed files are treated as empty input so startup does not fail merely
because optional sample files are absent.


CONTENT MUTATIONS AND AUDIT

ContentService supports list, read, add, update and delete. Standard users may list
and read; admins may also mutate. Add and update validate required fields, ISO
dates, death-after-birth chronology and positive facility ids.

Every listed row and successful individual read records READ. Every successful add
records CREATE and every successful update records UPDATE. Each change and its
audit insertion share a transaction. The audit schema intentionally has no foreign
key to content, allowing historical entries to survive later deletion. Delete is
not exposed through the menu and is not audited.

AGENT MESSAGES

  messages
    id INTEGER PRIMARY KEY AUTOINCREMENT
    agent_id INTEGER NOT NULL REFERENCES agents(id) ON DELETE CASCADE
    sender TEXT NOT NULL
    body TEXT NOT NULL
    created_at TEXT NOT NULL

A message is addressed to an agent. sender is the username of the logged-in user
who wrote it, taken from the session, and created_at is the local date and time
as ISO text (YYYY-MM-DDTHH:MM:SS), recorded when the message is stored.

SqliteMessageService.initialize() creates the table with CREATE TABLE IF NOT
EXISTS, so repeating it keeps existing messages. It runs after
SqliteContentService.initialize(), because the foreign key points at agents.
Messages are not a ContentType and are not audited; the shared content menus
never read this table.

Reading is by name, not by id. A user's inbox is every message whose agent's name
equals the logged-in username, ignoring case:

  SELECT m.id, m.agent_id, a.name, m.sender, m.body, m.created_at
  FROM messages m JOIN agents a ON a.id = m.agent_id
  WHERE LOWER(a.name) = LOWER(?) ORDER BY m.id DESC

The parameter is always the session's username and never text the user typed, so
no one can ask for another user's messages. Administrators have no extra access.
Newest messages come first. Usernames are limited to letters, numbers,
underscores and hyphens, so SQLite's ASCII-only LOWER is enough.

Sending checks that the agent exists and that the text is not blank, then inserts
one row. Deleting an agent would delete its messages, but agent delete is not
exposed through the menu.
