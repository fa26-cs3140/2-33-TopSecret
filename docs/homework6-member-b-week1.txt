CONTROLLER CONTRACTS

controller.LaunchMode.fromArguments(args)
  No arguments (or null): TERMINAL. Exactly -web: WEB. Exactly --change-password:
  CHANGE_PASSWORD. Other or combined arguments: IllegalArgumentException with
  usage text. The existing password-change workflow must remain available.

controller.WebAuthentication
  hasAccounts(): true only when at least one stored account exists.
  authenticate(username, password): canonical account username on success;
  Optional.empty() on rejection. IOException represents storage/validation
  failure, not bad credentials. Never log passwords or return them to a browser.
  An adapter will delegate to existing AuthenticationService; the contract does
  not introduce a second account store or change current username matching.
  Accounts requiring an initial password must complete that step in the terminal.

controller.WebSessionStore
  create(username): new opaque, unpredictable token mapped to the username.
  usernameFor(token): empty for null, unknown, invalidated or malformed tokens.
  invalidate(token): remove the association; unknown tokens are harmless.
  Week 2 implementation: in-memory, concurrency-safe storage; never use a username
  or password as a token. Resolve the current account and role through the model
  for each protected request. Tokens carry no trusted client-provided role.

controller.WebServerController
  PORT = 3002; SESSION_COOKIE = TopSecretSession.
  start(): refuse startup with IOException before binding if there are no
  accounts or credential storage cannot be validated. Instruct the user to create
  accounts through the terminal. Bind the production server to localhost:3002.
  address(): bound address after startup; tests may request an ephemeral port 0.
  close(): release listener and session state, including after startup failure.
  Lifecycle and HTTP implementation remain week 2 work; this is an interface.

PROPOSED HTTP ROUTES FOR TEAM REVIEW

  GET  /          Public login form, or redirect an authenticated user to /menu.
  POST /login     Decode username/password as UTF-8 form data and authenticate.
  GET  /menu      Protected read-only application navigation.
  GET  /content   Protected list: ?type=briefs|agents|facilities|missions.
  GET  /record    Protected detail: ?type=...&id=<positive integer>.
  GET  /audit     Protected audit display; retain existing administrator checks.
  POST /logout   Invalidate token, clear cookie, redirect to /.

Successful login: 303 Location: /menu and one Set-Cookie header:
  TopSecretSession=<opaque token>; Path=/; HttpOnly; SameSite=Lax
Omit Expires and Max-Age on the login cookie so it is a browser-session cookie.
Browser session restore behavior is controlled by the browser. The server must
not claim it can detect a browser closing. Logout and server restart invalidate
server-side access. A deployment using HTTPS should also use Secure; local HTTP
tests must be able to send the cookie on http://localhost:3002/.

Invalid credentials: 401 plus a generic error; no session is issued. Missing or
unrecognized cookie on protected routes: 303 to /. Invalid form or query: 400.
Authenticated role denial: 403. Unknown route: 404. Unsupported method: 405 with
Allow. Credential/backend failure: a generic 500 response without internal data.
Only login and logout accept POST; content is read only. Validate methods and
parameters before invoking model operations. Apply the login guard to every
protected route, including record and audit routes, not just the menu.
