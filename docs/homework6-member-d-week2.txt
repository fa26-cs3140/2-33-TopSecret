HOW MESSAGING WORKS

Sending: from the main menu, option 9 lists every agent by ID and name. The
user picks an ID and types the message. The sender is the logged-in username,
taken from the session, and the time is recorded when the message is stored.

Reading: option 10 lists the messages addressed to the agent whose name equals
the logged-in username, ignoring case, newest first. A user called ghost,
Ghost or GHOST reads the messages sent to the agent Ghost. A user whose name
matches no agent sees "No messages."

Privacy: the inbox is filtered by the session's username, never by anything
typed in the menu, so there is no way to ask for another user's mail. Admins
get no special access to it.

Access: sending and reading need a login but not admin rights. With no
session, every operation is refused with "Access denied."


SCHEMA

  messages
    id INTEGER PRIMARY KEY AUTOINCREMENT
    agent_id INTEGER NOT NULL REFERENCES agents(id) ON DELETE CASCADE
    sender TEXT NOT NULL
    body TEXT NOT NULL
    created_at TEXT NOT NULL      ISO local date-time

The table lives in data/missions.db beside agents. It is created by
SqliteMessageService.initialize(), which TopSecret runs after the content
service has created agents. Messages are not a ContentType, because
ContentType backs the shared Briefs, Agents, Facilities and Missions menus
and messages are private to one user.

KNOWN LIMITS

Messages cannot be edited, deleted or marked read. The web view does not show
them. A message can only be read by a username equal to the agent's name, so
an agent whose name is not a valid username could never receive one; every
seeded agent name is valid. Options 9 and 10 were numbered clear of the admin
options 5 to 8, so standard users see a gap in the menu numbers.
