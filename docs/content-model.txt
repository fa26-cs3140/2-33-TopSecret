Content and Relationship Model

DOMAIN OBJECTS

Brief stores id, title, date and text. Facility stores id, name and abbreviation.
Agent stores id, name, birth date, optional death date, notes and one facility ID.
The objects are immutable and validate required constructor values.

Briefs and missions have separate records. A brief may be attached to one mission
through briefs.mission_id; a mission may have zero or more attached briefs.
Deleting a mission clears that reference and preserves its briefs. Missions are
searchable records imported from mission_briefs.tsv, while briefs may be created
through the terminal.

A mission's facility and agents are reached through ContentService rather than
through a value object. MissionAssignment used to model that relationship and
was removed in homework 6: nothing constructed it, and its constructor rejected
an empty agent list and a facility ID below one, so it could represent neither a
mission with no agents yet nor one with no facility yet. Both are states
ContentService.add reaches when it is called directly, which is why the terminal
menu no longer offers mission creation and sets the relationships explicitly
instead.


MISSION RELATIONSHIPS THROUGH CONTENTSERVICE

  briefsFor(missionId, session)        the briefs attached to a mission
  attachBrief(missionId, briefId, s)   move a brief onto a mission
  facilityFor(missionId, session)      the facility running a mission
  setFacility(missionId, facilityId, s) record which facility runs it
  agentsFor(missionId, session)        the agents on a mission, any facility
  assignAgent(missionId, agentId, s)   put an agent on a mission

Reads require the role that can read content and are audited like other reads.
Writes require the role that can create content. A read of an unknown mission
answers empty rather than failing, since a mission with no relationships and a
mission that does not exist are the same to a caller with no reason to tell
them apart. A write naming a row that does not exist is refused.

The terminal mission menu reads these relationships and lets administrators set
a facility, assign an agent and attach a brief to an existing mission. Mission
creation remains hidden until a single model operation can save the mission and
its required relationships together.


SAMPLE IMPORT

SqliteContentService reads facilities.tsv and agents.tsv through FileHandler and
imports each target only when its table is empty. Named agent dates such as
"June 14, 1985" are normalized to ISO YYYY-MM-DD.

Because the supplied seed files do not include relationship IDs, imports use a
deterministic round-robin mapping. Agents receive facilities in file order.
Missions receive facilities and initial agents in ID order. With the supplied
files, this creates 6 facilities and 10 agents, and gives all 100 sample missions
one facility and at least one agent.

Table creation is committed before seed loading. Facility rows, agent rows and
mission relationships then load in one transaction. A malformed row or SQL failure
rolls back the complete seed transaction. Missing seed files are treated as empty
input so startup can continue.


RELATIONSHIP INTEGRITY

agents.facility_id is required and references facilities.id with ON DELETE
RESTRICT. mission_facilities uses mission_id as its primary key, allowing at most
one facility mapping per mission. mission_agents uses (mission_id, agent_id) as a
composite key, allowing multiple unique agents per mission. The optional
briefs.mission_id foreign key links a brief to a mission and is set
to NULL if that mission is deleted. Administrators can attach a brief, set a
mission's facility and assign agents through ContentService; agents may come from
any facility and can serve on more than one mission.

Relationship rows cascade only when their parent mission is deleted. Facilities
and agents use restrictive foreign keys. Protective triggers reject direct removal
of a mission's facility relationship or final agent relationship while that
mission exists. Every service connection enables PRAGMA foreign_keys = ON.


CONTENT OPERATIONS AND AUDIT

ContentService exposes list, read, add, update and delete. Standard sessions may
list and read; administrator sessions may mutate. Add and update validate required
fields, ISO dates, death-after-birth chronology and positive facility IDs.

List records one READ per returned row. Read records one READ after finding the
requested ID. Creation and update each share one transaction with their CREATE or
UPDATE audit event. Delete is only available at the service boundary and is not
recorded.
