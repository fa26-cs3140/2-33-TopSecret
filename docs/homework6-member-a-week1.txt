ENTITY AND RELATIONSHIP DECISIONS

A mission is one row in missions, created by SqliteMissionRepository and shared
with the content menu through ContentType.MISSION with fields title, brief and
date. The searchable mission archive and the content menu read the same table.

A mission is run by exactly one facility. mission_facilities carries a primary
key on mission_id, so the schema already makes a second facility impossible.

A mission has at least one agent, through mission_agents.

A mission may have zero or more briefs. This is new in homework 6 and is the
only relationship requiring a schema change.

MissionAssignment modelled a mission with its facility and its agent IDs and
was the obvious type to reuse. It was removed instead: its constructor rejects
an empty agent list and a facility ID below one, so it cannot represent a
mission that has no agents yet or no facility yet, and both are states
ContentService.add reaches. The relationships are read through ContentService.


SCHEMA CHANGES

One column:

  ALTER TABLE briefs ADD COLUMN mission_id INTEGER NULL
      REFERENCES missions(id) ON DELETE SET NULL

Nullable because zero briefs is a legal mission and an unattached brief is a
legal brief; briefs existed before missions did and the seed data has rows of
both kinds. ON DELETE SET NULL rather than CASCADE because a brief is a record
in its own right and deleting a mission should not destroy its paperwork.

A single nullable column, not a join table: a brief belongs to at most one
mission, so a join table would need a unique constraint on brief_id to say the
same thing in two tables.

No other table changes. mission_facilities, mission_agents and both protective
triggers stay as they are.


MODEL CONTRACTS

Six methods on ContentService. ContentMenu tests mock the interface, so adding
to it does not disturb Members B, C or D.

  briefsFor(missionId, session)
    The briefs attached to that mission, empty when there are none. An unknown
    mission ID returns an empty list rather than failing; a mission with no
    briefs and a mission that does not exist look the same to a reader with no
    reason to tell them apart.

  attachBrief(missionId, briefId, session)
    Point an existing brief at an existing mission. Requires the role that can
    update content. Re-attaching a brief moves it; a brief has one mission.

  facilityFor(missionId, session)
    The facility running the mission. Empty when the mission has no
    mission_facilities row, which is possible for missions created before
    item 4 lands.

  setFacility(missionId, facilityId, session)
    Write the mission_facilities row. Requires the role that can create or
    update content. Replaces any existing row, since the primary key permits
    only one.

  agentsFor(missionId, session)
    The agents assigned to the mission, from any facility.

  assignAgent(missionId, agentId, session)
    Add a mission_agents row. Idempotent; assigning the same agent twice is not
    an error. The agent need not belong to the mission's facility.

Every one takes a Session and goes through the same AccessControl checks the
existing methods use. Reads record to the audit log the way other reads do.


THE FACILITY GAP

Making missions creatable through the generic add path introduced a defect
worth stating plainly. ContentService.add writes the missions row and nothing
else, so a mission created from the menu has no mission_facilities row and
therefore no facility, which contradicts the rule that a mission is run by one
facility. The protective trigger does not catch it: the trigger fires BEFORE
DELETE on mission_facilities, and a row that was never written cannot be
deleted.

Item 4 fixes this by prompting for a facility during mission creation and
writing both rows in one transaction. Until then, every mission the seed
importer creates has a facility and every mission a user creates does not.


JOINT OPERATIONS

The assignment requires that a mission run by one facility may use agents from
any facility. No schema work was needed. agents.facility_id and
mission_facilities.facility_id are independent columns, and no constraint,
index or trigger relates them. Agents belong to one facility and may serve on
multiple missions; mission_agents has a composite primary key, not a unique
constraint on agent_id.

This is correct by omission rather than by design, so it now has tests that
fail if someone later adds the constraint that feels natural: an agent from one
facility assigned to a mission run by another, one agent on two missions, and
one mission drawing agents from two facilities. They are in
SqliteContentServiceAgentTest and passed the moment they were written, which is
the point of them.


KNOWN DUPLICATION

missions.brief holds a mission's brief text, and the briefs table holds brief
records. mission_briefs.tsv seeds both, so the same text is stored twice.

This is deliberate for homework 6. The mission archive and its word search read
missions.brief, and that search is a graded homework 4 feature; removing the
column means rewriting MissionSearchService and eleven other files mid-
assignment. The honest normalization is to delete missions.brief and let a
mission reach its text through briefs.mission_id. Proposed for homework 7.
